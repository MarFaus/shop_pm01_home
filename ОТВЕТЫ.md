# Ответы на контрольные вопросы

## Лаб 1

**1. Образ и контейнер, тома.** Образ — неизменяемый шаблон (файлы + команда запуска), контейнер — запущенный экземпляр образа со своим слоем для записи. Том (`pgdata`) хранит данные отдельно от контейнера. После `docker compose down` контейнеры удаляются, а том остаётся, и база при следующем запуске на месте. После `docker compose down -v` удаляется и том: база пересоздаётся с нуля из `db/init`.

**2. localhost:5432 и postgres:5432.** Локально uvicorn работает на компьютере, а порт базы проброшен на компьютер (`5432:5432`). Внутри контейнера `localhost` — это сам контейнер приложения. Сервисы compose живут в общей сети и находят друг друга по имени сервиса, поэтому из `app` база доступна как `postgres:5432` (внутренний порт).

**3. Зачем requirements.txt копируется отдельно.** Docker кэширует слои. Пока `requirements.txt` не менялся, слой с `pip install` берётся из кэша, и правка `main.py` пересобирает только последний слой `COPY . .`. Сборка занимает секунды вместо минуты.

**4. FOR UPDATE.** Блокирует строку товара до конца транзакции: второй покупатель ждёт, пока первый не спишет остаток. Без блокировки оба прочитают `stock = 1`, оба пройдут проверку и оба спишут товар, и остаток станет `-1` (продали больше, чем было).

**5. p95.** 95% запросов выполнились быстрее этого значения. Среднее прячет «хвост»: при среднем 25 мс часть пользователей ждёт 200+ мс. В Лаб 1 среднее было 25 мс, а p95 — 168 мс. p95 показывает, что ощущают самые невезучие пользователи.

**6. Узкое место.** postgres: в `docker stats` у него до 800% CPU (8 ядер), у остальных намного меньше. Его грузят тяжёлые запросы `top-products` (агрегация по 500 000 заказов) и `ILIKE '%...%'` без индексов. Приложение к пику тоже упёрлось в свой лимит 0,5 ядра (50% CPU).

## Лаб 2

**1. Рост RPS.** У нас RPS почти не изменился (238 → 240). Тест сам ограничивает поток: в среднем ~30 VU, и каждый после запроса спит 0,1 с, поэтому больше ~245 RPS он не даст. При этом нагрузка на воркер упала с 50% до ~21% CPU, то есть запас появился. Втрое RPS не растёт и в общем случае: общая база одна, она и есть узкое место, плюс накладные расходы балансировщика. Узкое место — по-прежнему postgres.

**2. least_conn.** Запросы у нас очень разные по времени: карточка товара — 3 мс, заказ — 200 мс, топ — 80 мс. Round-robin раздаёт запросы по очереди и может навалить несколько долгих на один воркер. least_conn отдаёт новый запрос тому, у кого меньше активных, и нагрузка выравнивается.

**3. Почему POST не повторяется.** POST создаёт заказ. Если воркер упал после записи в базу, но до ответа, повтор на другом воркере создаст второй заказ и второй раз спишет товар. GET безопасно повторять: он ничего не меняет.

**4. Корзина в переменной Python.** У каждого воркера своя память, а следующий запрос пользователя может попасть на другой воркер: корзина «пропадёт» или будет разной. При перезапуске воркера она исчезнет совсем. Решение — хранить состояние вне процесса: в БД или в Redis (Лаб 3), а клиенту отдавать только идентификатор сессии.

**5. Единая точка отказа.** База PostgreSQL (одна) и сам балансировщик Nginx (один). Упадёт любой из них — магазин недоступен. Реплики БД появятся в Лаб 6.

Опыт с отказом: при `docker compose stop app2` под нагрузкой k6 показал 0 ошибок. uvicorn по сигналу остановки дорабатывает начатые запросы, а Nginx (`proxy_next_upstream`) повторяет GET на другом воркере и после ошибок исключает app2 на 10 секунд.

## Лаб 3. Кэш Redis

**Что такое cache-aside?** Приложение само управляет кэшем: ищет ключ в Redis → если нет (MISS), читает из БД и кладёт в Redis с TTL → при изменении данных удаляет ключ. Код — `app/cache.py` и обработчики в `app/main.py`. Заголовок ответа `X-Cache: HIT/MISS` показывает, откуда ответ.

**Зачем TTL и как выбран?** TTL ограничивает, насколько устаревшими могут быть данные, и не даёт кэшу хранить ненужное вечно. Карточка товара — 60 с (плюс удаление при заказе), список категории и топ продаж — 30 с (отставание на полминуты допустимо), поиск — 60 с.

**Что такое инвалидация?** Удаление ключа, когда данные в БД изменились. После заказа удаляем `product:{id}`: остаток изменился, следующий запрос возьмёт свежие данные из БД. Списки не инвалидируем, их «лечит» короткий TTL.

**Что будет, если Redis упадёт?** Магазин продолжит работать, только медленнее: все ошибки Redis перехватываются, запрос идёт в БД. Кэш — ускоритель, а не хранилище. Поэтому в Redis отключено сохранение на диск, а `maxmemory` + `allkeys-lru` вытесняет редко читаемые ключи.

**Почему вырос RPS и упал CPU postgres?** 80% просмотров приходится на 1000 «горячих» товаров, они почти всегда в кэше. CPU postgres упал с ~780% до 30%.

## Лаб 4. Redis Cluster

**Как кластер делит данные?** Пространство ключей — 16 384 слота, слот = CRC16(ключ) mod 16384. Каждый из 3 мастеров отвечает за треть слотов. Клиент (`RedisCluster` в `cache.py`) сам вычисляет слот и идёт на нужный узел. Проверка: `docker compose exec redis1 redis-cli cluster nodes`, ключи разошлись по мастерам примерно поровну.

**Зачем 6 узлов?** 3 мастера (шардирование — больше памяти и пропускной способности) + по реплике на каждый (отказоустойчивость). 3 — минимум мастеров для голосования при failover.

**Что происходит при падении мастера?** Через `cluster-node-timeout` (5 с) остальные мастера признают его упавшим, и его реплика становится мастером. Опыт: под нагрузкой остановили redis5 — 0 ошибок, вернувшийся узел встал репликой. Чтобы во время переключения пользователь не ждал, на операции кэша стоит потолок 0,3 с: без него отдельные запросы висели до 10 с.

**Почему в конфиге `cluster-preferred-endpoint-type hostname`?** IP контейнеров меняются при пересоздании, а имена (redis1…) постоянные.

## Лаб 5. RabbitMQ

**Зачем очередь?** Медленная часть (платёжный шлюз, 0,2 с) уходит из запроса пользователя. API резервирует товар, сохраняет заказ со статусом `pending`, кладёт номер в очередь и сразу отвечает `202 Accepted`. `consumer.py` выполняет оплату и ставит `processed`. p95 заказа упал с ~210 до ~25 мс.

**Как не потерять заказ?** Очередь `durable`, сообщения `persistent` (переживут перезапуск RabbitMQ), `publisher_confirms` (API ждёт, что брокер принял сообщение). Подтверждение (ack) consumer отправляет только после записи в БД. Если публикация не удалась, заказ уже в БД, и consumer раз в минуту переотправляет «застрявшие» pending.

**Что если сообщение придёт дважды?** `UPDATE ... WHERE id = $1 AND status = 'pending'` — повтор ничего не изменит (идемпотентность). Сообщение, обработка которого упала с ошибкой, уходит в `orders.dead` (dead letter queue), а не крутится по кругу.

**Что такое prefetch?** Сколько неподтверждённых сообщений consumer берёт сразу. 50 — пока одно ждёт шлюз, обрабатываются остальные: ~250 заказов/с.

**Что показал всплеск 300 заказов/с?** Воркеры не успевали, очередь выросла до ~1200 и была разобрана за ~10 с после теста. Очередь сглаживает пики.

## Лаб 6. Реплики PostgreSQL

**Как работает потоковая репликация?** Primary пишет все изменения в журнал WAL и передаёт его репликам. Реплика при первом старте копирует всю базу (`pg_basebackup`, `db/replica-entrypoint.sh`), затем непрерывно применяет WAL. Отставание у нас — единицы миллисекунд (`pg_stat_replication`).

**Как разделены чтение и запись?** `app/db.py`: каталог, поиск и статистика читаются с реплик по очереди, заказы пишутся в primary. Запись на реплику невозможна: `cannot execute INSERT in a read-only transaction`.

**Почему `GET /orders/{id}` читает с primary?** Read-your-writes: покупатель сразу после создания заказа запрашивает его, а реплика могла ещё не получить запись.

**Что будет при падении реплики? А primary?** Реплики: запрос уходит на другую реплику или primary, упавшая пропускается 10 с — опыт показал 0 ошибок. Primary: запись невозможна, чтение продолжает работать. Автоматическое повышение реплики до primary (Patroni и т.п.) в проекте не делали — это следующий шаг.

## Лаб 7. PgBouncer и тюнинг

**Зачем PgBouncer?** Каждое соединение с PostgreSQL — отдельный процесс (~5–10 МБ), их число ограничено `max_connections`. PgBouncer принимает тысячи дешёвых клиентских соединений и раздаёт им небольшой пул настоящих. Стресс 300 VU: 78 клиентов у PgBouncer → 34 соединения с базами.

**Режимы пула?** session — соединение закреплено за клиентом до отключения; transaction — только на время транзакции (наш выбор, самый экономный); statement — на один запрос. В режиме transaction нельзя держать состояние сессии. Подготовленные выражения asyncpg PgBouncer 1.21+ переносит сам (`max_prepared_statements`).

**Что нашли через pg_stat_statements?** asyncpg после КАЖДОГО запроса слал `RESET ALL; pg_advisory_unlock_all(); CLOSE ALL` — столько же вызовов, сколько полезных запросов. Отключили (`reset=_no_reset` в `db.py`): состояния сессии у нас нет.

**Что дали индексы?** См. таблицу в ЖУРНАЛ.md: список 17 → 0,25 мс, поиск без совпадений 64 → 0,56 мс (GIN по триграммам — B-tree не умеет `LIKE '%...%'`), топ продаж 115 → 42 мс (Index Only Scan благодаря `INCLUDE`).

**Что изменено в postgresql.conf?** `shared_buffers` ~25% памяти, `random_page_cost = 1.1` (SSD — индексы выгоднее), `jit = off` (на коротких запросах JIT только тратит время), `pg_stat_statements`, лог медленных запросов > 500 мс.

## Лаб 8. CDN и мониторинг

**Как работает edge-кэш?** `edge/default.conf`: nginx перед балансировщиком кэширует ответы каталога на 10 с («микрокэш»). `proxy_cache_lock` — за устаревшим ответом к origin идёт один запрос, а не сто. `proxy_cache_use_stale` — если origin упал, отдаётся старая копия. Заголовок `X-Cache-Status: HIT/MISS`. Edge принял на себя ~60% запросов, CPU воркеров упал вдвое.

**Минусы CDN-кэша?** Данные могут отставать на TTL (остаток товара — до 10 с). Инвалидацию из приложения (удаление ключа при заказе) edge не видит — у настоящих CDN для этого есть purge API. Персональные данные (заказы, корзина) кэшировать нельзя, поэтому кэшируются только `/products` и `/stats`.

**Как устроен мониторинг?** Приложение отдаёт метрики на `/metrics` (счётчик запросов, гистограмма времени ответа по маршрутам, попадания в кэш). Экспортеры переводят статистику PostgreSQL, Redis, nginx в формат Prometheus, у RabbitMQ встроенный плагин. Prometheus опрашивает всех раз в 5 с, Grafana рисует дашборд «Мини-магазин».

**Почему p95 считают из гистограммы, а не храня все времена?** Гистограмма — это счётчики по корзинам (≤5 мс, ≤10 мс…). Их можно складывать между воркерами и по времени, а `histogram_quantile` оценивает перцентиль. Хранить каждое значение слишком дорого.

**Почему метка — шаблон маршрута, а не путь?** `/products/{product_id}` вместо `/products/123`: иначе каждый товар стал бы отдельным временным рядом (200 000 рядов — «взрыв кардинальности»).
